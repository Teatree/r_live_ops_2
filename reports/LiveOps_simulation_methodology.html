How every number in the sim is produced

A per-segment, per-resource comparison of the calendar that runs today against the redesign — and, since September, of two features that had never run at all: the card collection and Tower of Fortune. This document explains the method behind every cell, why each modelling choice was made, and where the assumptions are buried.

Part A

The model and the machinery every source shares

One equation, four terms, and a small set of shared helpers. Everything in Part B is a variation on this page.

1Anchor on telemetry, simulate only what changed

The simulation compares two 33-day LiveOps calendars — cal_curr (what runs today) and cal_new (the redesign) — per engagement segment × payer flag × source category × resource. The output unit is per-earner gains over the 33-day window: what a player who earned this resource from this source got, on average.

the central equation, for an anchored source
SIMULATED[res]  =  measured[res]  ×  R[res]  ×  D  ×  T
                    ↑              ↑         ↑      ↑
                telemetry      reward     duration  cadence

Anchoring means we never price a live event's rewards bottom-up from config when telemetry exists; we only scale reality by what changed. That automatically absorbs mechanics nobody can model — matchmaking, rank distributions, endless gates, loop grinding — because they are already inside the measured number.

Four fates, not one

Not every source is anchored. The registry decides which of four things happens to a category, and the difference matters more than any single formula:

The three departures from anchoring
  • Carried — nothing changed, or there is no schedule: SIMULATED = measured, DIFF = 0.
  • Bottom-up — no valid anchor is possible. Rainbow Maker (brand new), the six envelope tiers, ToF_Ticket, and Tower of Fortune itself are priced from their config ladders against a population distribution.
  • Removal — a simulated event with zero cal_new instances returns 0. Since D34 that branch requires cal_curr to actually run the event: a source absent from both calendars is outside the comparison and is carried, not zeroed. River Rush was the live case — it was reporting −109 HC at 100+ PAYER for a removal that no longer meant anything.

2Registry and dispatch — one function per source

CATEGORY_ORDER drives the spill order and must match the EcoGainsSim sheet's row labels exactly. The SOURCES registry maps each category to its own named simulator; anything unlisted is carried. Decision D15 made this one-function-per-source on purpose: a source's whole model should be readable in one place.

measured — the anchor

The telemetry ground truth for the CURRENT calendar: amount_per_earner for this (segment, payer, category, resource). SIMULATED is a scaling of this number for every anchored source, and DIFF = SIMULATED − measured is the headline output. A missing row is a real measured 0, not a bug.

R — the reward ratio

What it represents: how the reward config changed, per resource. R[res] = E_v2 / E_base, where E is the ladder's expected payout for this (segment, payer) under the measured player distribution. Because the base sheet holds the config that produced the measured anchor, R = 1 exactly until a _v2 reward or requirement is edited.

two flavours of E, by family
leaderboards  E[res] = Σk P(rank = k) × ladder_payout(k)      rank CDF × the prize table
collections   E[res] = Σk S(req_k) × reward_k[res]            survival × the milestone ladder

Because the rank / progress distribution is held fixed across base and v2, R isolates the reward-per-rank change and nothing else. Kite additionally prices a score-milestone term. Base-0 → v2-positive rule: if E_base = 0 but E_v2 > 0 there is no anchor to scale, so the resource is carried — which is why adding new milestone rewards to TaD_v2 will not flow.

Worked — leaderboard R (Red Challenge, 40-99)

Ladder (Race, HC by rank): 1→200, 2→100, 3→50, 4–10→20, 11+ → not on the board. Where this segment finishes: ranks 3, 8, 15.

E_base[HC] = (50 + 20 + 0)/3 = 23.3 — rank 15 is past the top-10 board, so it contributes 0. If Race_v2 nerfs those ranks to 40 / 15 / 0 then E_v2[HC] = 18.3 and R[HC] = 0.79.

That is the pre-D27 arithmetic, shown because it is the clearest way to see what R is. Since 2026-09-02 the three quantiles are anchors of a distribution rather than the only ranks priced — see below.

D — the duration multiplier

D = curveShare(newDur) / curveShare(curDur), normalised at the current modal duration. curveShare(day) is the median fraction of a participant's own eventual instance total earned by day N, from the accrual curve.

  • Only collections use a real D. Leaderboards pin D = 1: rank payouts are end-state, and more days barely move relative rank.
  • Shortening is interpolation on observed days — reliable. Lengthening is extrapolation past observed days — low-confidence, and moot today because every lengthening case sits on a saturated curve.
  • The curve is a p50 curve, so tail behaviour (heavy loopers on an added day) is invisible. Flagged, accepted.

T — cadence and reach

T = Σnew reach(inst) / Σcur reach(inst), summed over the event's instances in each calendar. It is not an instance-count ratio — a longer run catches more of a non-daily population, and weekend slots reach differently from weekday slots.

reach and p_day

reach(inst) = 1 − Πdays in inst (1 − p_day)   the complement trick
p_day       = weekend_active_rate on Fri/Sat/Sun, else weekday_active_rate
weekend rule: both calendars start Wednesday, so day d is a weekend when ((d−1) mod 7) ∈ {2,3,4}

S — the survival function

survival_(points) builds S(x) = 1 − CDF(x) from a piecewise-linear CDF through (0,0) plus the given (x, percentile) points, with a linear tail beyond the last point at the preceding slope, capped at 1. S(req) is the fraction of players whose relevant quantity reaches threshold req. One implementation, four distributions: collection and leaderboard progress, Night Sky streaks, Rainbow Maker matchables, Daily Gift login streaks.

The rank distribution — D27, and why it replaced three atoms

Until 2026-09-02, lbE_ priced a leaderboard as the mean payout at exactly three integer ranks (position_p25/p50/p75, weight ⅓ each). That is not a distribution, and on a top-heavy ladder it failed in both directions at once.

Why not a parametric fit — and the bias that remains

100+ Red has p25 = p50 = 1: at least half that segment's finishes are 1st. A lognormal least-squares through those anchors returns P(1) = 0.33, contradicting a fact the data states outright. The linear CDF honours every anchor exactly and assumes nothing else.

Flagged: real rank distributions are unimodal, so where p25 is deep (0-9, p25 = 5) the true density at rank 1 is below the [1, p25] average and this reads a little high — 0.05 per instance. Bounded by construction, and it replaces an exact 0.

D27a, found by the gates rather than by reading: LB_R_SPECS declares Flash Race as rows 81–90, but the sheet ends at 87. The ordinal fallback read three missing rows as ranks 8, 9 and 10 — invisible under three atoms, but under a distribution they take 12.5% of the mass and pay nothing for it. A row that does not exist is not a rung.

E and E_day

E is an expected ladder payout per resource under a population distribution — the building block of both R and every bottom-up sim. E_day is Night Sky's per-active-day version. rewardR_ was deliberately split into rewardE_ (the absolute expected payout, both sides) plus a thin ratio wrapper, so the pack lane reuses lbE_ / collE_ verbatim and an envelope typed into a _v2 ladder is priced with exactly the machinery that prices a coin on the same row.

modalDur

The most common instance duration in a calendar for one event, fed to D. A lone clipped instance — a 2-day fragment of a longer run cut by the window edge — is outvoted by the modal duration so it cannot distort D, but its real day list is still used for reach.

NS_STREAK_N and the day-type switch

NS_STREAK_N = 1.25: a player tends to land roughly a second streak of similar size over a day, and the factor absorbs streak resets. Every streak percentile is multiplied by it before S is built. NS_V2_WEEKDAY_SHEET + NS_DAYTYPE_SPLIT are the "two Night Skies" switch — see §6.7.

The verified merge rule

Robustness, learned the hard way

  • Custom functions sometimes cannot read merges, so menu EcoGainsSim ▶ Precompute calendars parses with full permissions and writes the instances to a hidden cal_parsed sheet, which the engine prefers. Re-run it after editing merges — value edits fire onEdit, merge edits fire nothing.
  • Namespace collision trap. All Apps Script files share one global scope; a test file defining parseCalendarInstances_ with a different shape once silently overrode the engine's parser.   • A cloned workbook can ship a stale cal_parsed. It is preferred over live parsing, so the clone will happily simulate the calendar its parent had.
§4.3 — the parse canary

The Kite Festival row must DIFFER from measured. It equals measured × R × T; with the real Ki_v2 edits that is ×0.833 × 1.31 ≈ ×1.09. If every timed event row equals measured at once, the calendar read failed — run Precompute.

6.2Core and Saga

Core: carried Core SPT: synthetic anchor Saga: anchored 📊 data_gains📊 data_seg_beh ⚙ c_saga / c_saga_v2⚙ SP / SP_v2 panel

data_gains splits base-game progression into Core (chapter_complete, PlayerLevelUpChest, and level-completion SPT) and Saga (the SagaPath nerf line). Both are always-on, so D = T = 1.

Saga — a pure ladder-vs-ladder ratio

  1. measured from data_gains.
  2. HC ratio = cycleAvg(c_saga_v2) / cycleAvg(c_saga), where cycleAvg = ΣHC_reward / ΣLevels_req over the node ladder — "coins per level". The v2 ladder is segmented (D14): readSagaV2_(seg) picks that segment's own column pair.
  3. item ratios = Σ v2 item / Σ base item per level. Column missing in v2 → carry (never zero on a layout edit); base total 0 → carry (no anchor).
The saga readers are header-driven since 2026-08-13 — re-paste the engine

Workbook (15) rebuilt c_saga / c_saga_v2 in a triple-column layout (Levels Req | RewardChestId | HC Reward per segment block). The old fixed-column read silently priced chest IDs as HC, which put Saga R at ×7–10. Both engine copies now find columns by header. A live Apps Script project that has not been re-pasted still carries the old reader.

Core SPT — the synthetic anchor (D17 / D18)

Core's chapter and level-up chests are unchanged, so they are carried. But every level completion also pays a difficulty-tiered season-pass token, and data_gains has no Core SPT rows — the export cannot see the level-token faucet, though the live game pays it. Rather than let a real faucet read as zero, measuredRow_ rebuilds the measured side from behaviour telemetry.

In plain words

Core is what you get for finishing chapters, levelling up, and — the part we model — the season-pass tokens you get for beating a level, bigger the harder the level. The export simply does not carry those rows, so we estimate today's number: how many levels a typical player of this segment beats over 33 days, times the expected tokens per level. That is the "today" figure; the redesign figure is the same level count at the new per-level rewards. Saga is simpler — per level played, how much does the new ladder pay compared to the old one? Players who only got halfway along the path in real life are still only halfway along in the simulation, because their real progress is baked into the measured number.

the formula
Core      SIMULATED[res] = measured[res]        except SPT
Core SPT  measured = L × E_base      SIMULATED = L × E_v2
             L = levels_per_active_day × Σ p_day

Example 1 — Saga coins, 40-99 nonpayer

The base ladder pays 75 HC across the 100 levels of one cycle → 0.75 HC/level. The segment's c_saga_v2 columns pay 60 HC across the same 100 levels → 0.60. HC_ratio = 0.80. Measured saga coins 400.44 → 320.35 HC (DIFF −80.09): the player's real progress is kept, re-priced at the leaner tuning.

Example 2 — booster items, same segment: one mechanism, four different fates

Bomb drops 0.03 → 0.01 per level, ratio ⅓ → measured 5.77 becomes 1.92. Slingshot drops 0.01 → 0, ratio 0 → 4.31 becomes 0 (v2 deleted it, so the sim deletes it). Unlimited Lives is untouched, ratio 1 → the 577.02 minutes stay. UL Red pays 0 on the BASE ladder → no anchor, no ratio possible → its measured 0.0004 is carried unchanged.

6.3Daily Gift

anchored 📊 data_gains📊 data_seg_beh login_streak ⚙ c_day / c_day_v2

A 7-day login ladder whose HC values were re-tuned. Always-on (D = T = 1); only HC moves, weighted by how likely each ladder day is to be reached.

  1. Read both ladders. Identical → R = 1, stop.
  2. Build S over login_streak_p50/75/90. Weight wₙ = P(streak ≥ n) = S(n−1).
  3. R_HC = Σ(v2ₙ · wₙ) / Σ(baseₙ · wₙ).
  4. SIMULATED[HC] = measured[HC] × R_HC; every other resource = measured.
In plain words

Log in day after day and each day's gift gets bigger; miss a day and you restart. Comparing the two ladders by their plain totals would be wrong, because almost everyone sees day 1 and only very regular players ever see day 7. So we weight each ladder day by the share of players who actually reach it, take the weighted average of both ladders with the same weights, and divide. That is why casual players eat more of a nerf than the raw config suggests: the untouched day-7 gift protects mostly the players who get there.

Two segments, one config edit, two different answers

0-9 nonpayer. Ladders 22/0/0/27/0/33/100 → 10/0/0/10/0/10/100 (day 7 untouched). Streaks p50 = 2, p75 = 5, p90 = 10 give w₁…w₇ = 1, .75, .50, .417, .333, .25, .22. Weighted old 63.50, new 38.67 → R = 0.609 — harsher than the naive 130/182 = 0.714. Measured 120.66 → 73.47 HC.

40-99 nonpayer. Longer streaks (p50 = 3, p75 = 8, p90 = 20) fatten the late-day weights (w₇ = 0.35): weighted old 83.70, new 54.00 → R = 0.645. Measured 103.85 → 67.01 HC. Identical nerf on paper; the streakier segment escapes more of it — exactly the effect the survival weighting exists to capture.

6.4Score-based leaderboards — Kite Festival and Target Day

anchored · D pinned 1 📊 data_event_inst position + final_balance ⚙ Ki / Ki_v2 · TaD / TaD_v2 📅 both calendars

Both are score events: you accumulate a score across an instance and are paid at instance end. Kite pays by rank in a zero-sum league of 60 (fixed pot 875 HC per league); Target Day is structurally a milestone-plus-leaderboard hybrid, but its milestone ladder pays 0 by design today (D3), so it is simulated as a pure leaderboard. Both pin D = 1: rank payouts are end-state, so a longer instance barely moves what a given placement earns.

  1. simKiteFestival / simTargetDay → leaderboardSim_ → timedCore_ with the D-function pinned to 1.
  2. T from the two calendars' reach sums. Target Day's 3×7d → 15×1d gives T ≈ 1.8 — fifteen one-day boards are fifteen rank chances. Kite's 3×7d → 5×3d gives 1.31.
  3. R via rewardR_ → lbE_: build the rank CDF from position_p25/50/75, read the ladder from the Ki/TaD block and its _v2, E = Σk P(rank = k) × ladder(k) on each side. Kite additionally adds Σ S(scoreReq) × reward with S over final_balance, so milestone-reward edits on Ki_v2 flow.
Zero semantics

Low segments earn very little HC because they rarely place top-3 — check the booster columns before declaring a row dead. Since D27 a deep-finishing segment gets a small positive rather than an exact 0, because the rank CDF always assigns rank 1 some mass. An exact 0 now means the ladder pays nothing at all, or cal_new has no instances.

Example 1 — Kite Festival, 40-99 nonpayer: a ladder nerf that survives a cadence buff

Typical finishing ranks 3 / 6 / 14. Ki pays 150 HC + 240 SPT + 1 Shuffle · 140 SPT + 1 Slingshot · 90 SPT + 1 Chuck; Ki_v2 pays 125 HC + 150 SPT + 1 Shuffle · 90 SPT + 1 Slingshot · 60 SPT + 1 Red.

R_HC = 0.833, R_SPT = 0.638. The single score milestone (100 kite score → 30 min Unlimited Lives) is passed by virtually everyone — final scores start at p25 ≈ 19,424, so S(100) = 0.999 — and is identical on both sheets, contributing ratio 1. Calendar: T = 1.31.

HC 33.11 × 0.833 × 1.31 = 36.15. SPT 81.28 × 0.638 × 1.31 = 67.97. Chuck 0.018 × 0 = 0 — rank 14's Chuck was swapped for a Red, and since the base ladder pays no Red at these ranks there is no Red anchor, so the measured Red 0.014 is carried and just rides T.

Example 2 — Target Day, 40-99 payer: two dials, opposite directions

A pure rank event, no survival term at all. Typical ranks 1 / 2 / 5: TaD pays 200 HC + 1 Comet · 100 HC + 1 Shuffle · 1 Shuffle; TaD_v2 pays 50 HC + 1 Comet · 25 HC + 1 Shuffle · 1 Bomb. R_HC = 0.25.

Calendar: three boards (reach 2.31) become fifteen one-day boards all sitting Fri–Sun (reach 4.33) → T = 1.87. Net: 38.73 × 0.25 × 1.87 = 18.11 HC. The schedule nearly doubles this segment's opportunities and the top-rank nerf still outweighs it — one multiplication, two dials pulling opposite ways.

6.5Rank leaderboards — Bomb's, Chuck's, Red's, Level Race, Flash Race

anchored · D pinned 1 📊 data_event_inst position ⚙ Race / Race_v2 — five blocks, one sheet

Pure rank races: your payout depends on where you place from a fixed top-N pot, not on absolute accumulation. Identical to §6.4 minus the score-milestone term — so the survival function is never used in this family. Worked T values at 0-9: Bomb 0.86, Chuck 0.69, Red 1.30, Level 0.86, Flash 0.99.

Flash Race legitimately sims ≈ 0 in HC

Its real payout is SPT, tracked as its own column since D16. The coins zero is correct, not a bug. Before D16 the whole event read as dead.

Example 1 — Red's Challenge, 40-99 nonpayer: pure scheduling

Typical ranks 1 / 2 / 4; the table pays 200 HC + 1 Comet, 100 HC + 1 Shuffle, 1 Shuffle. Race_v2 is untouched, so R = 1 for every resource. Four one-day boards (reach 1.18) become three two-day boards (reach 1.52) → T = 1.28. HC 47.84 → 61.22. Chuck's Challenge is the same machinery pointing the other way: five boards shrink to two, T = 0.68, 11.98 → 8.16 HC.

Example 2 — Red's Challenge, 0-9 nonpayer: same event, different rank band

This segment typically finishes 5 / 10 / 14, and at those ranks the table pays no coins at all on both sheets. E_base[HC] = 0 → no HC anchor → the small measured 1.27 HC is carried through R and rides the schedule: 1.27 × 1.30 = 1.65 HC. The boosters price normally: Slingshot 0.214 × 1.30 = 0.28. A low segment earning ≈ 0 coins from races is real rank economics, not a missing row.

6.6Collections — Hatchling Hideaway, Jigsaw, Bomb's Ballet, Photoshoot

anchored · the only family where BOTH time dials turn 📊 data_event_accrual📊 data_event_inst final_balance ⚙ HH / J / BB / Ph + _v2

Accumulation-gated — bank enough tokens to claim milestones — but live with full telemetry, so they are anchored. Unlike leaderboards, duration matters: a shorter instance means less time to accumulate, and that enters through the D accrual curve. R uses the collection flavour (survival over progress), so both reward and requirement edits move the sim.

the formula
SIMULATED[res] = measured[res] × R[res] × D × T

  R[res] = E_v2[res] ÷ E_base[res],   E[res] = Σk S(reqk) × rewardk[res]
  S(x)   = 1 − CDF(x) over final_balance_p25/50/75
  D      = curveShare(newDur) ÷ curveShare(curDur)      at each calendar's modal duration
The requirement axis differs by sheet — and one half of it is flagged

Jigsaw and Bomb's Ballet read each sheet's own native cumulative requirement column, so requirement edits flow fully. Hatchling Hideaway and Photoshoot have no native cumulative req column on the base sheet, so both sides share the _v2 EventReach helper column as the axis: reward edits flow, requirement edits only re-weight. Bomb's Ballet also adds a completion row gated at the last milestone's requirement.

Example 1 — Jigsaw, 40-99 nonpayer (4d → 3d): the whole change is time, split in two

Accrual curve: day 1 27%, day 2 63%, day 3 92%, day 4 100% → D = 0.92. Schedule: T = 0.90. R: final balances 774 / 1,410 / 1,931 pieces give S(30) = 0.99 down to S(1,930) = 0.25 across twelve milestones — but J_v2 is identical to J, so the two expected payouts cancel and R = 1. The survival table is built and priced; it just moves nothing yet. HC 25.24 × 1 × 0.92 × 0.90 = 20.93.

Example 2 — Hatchling Hideaway, 0-9 nonpayer (3d → 4d): a saturated curve

Day 1 17%, day 2 71%, day 3 100% — by the old length the median participant has already banked everything they were going to, so the added day contributes nothing: D = 1 (the flagged extrapolation, here simply flat). T = 1.16. The survival side shows how shallow a casual's event is: final balances of 6.3 / 13.4 / 25.4 hatchlings mean S(20) = 0.36 for the first nest gate and S(51.25) = 0 for every later one — this segment's expected config payout is one partial gate. Stage 1 — acquisition, and the rounding bias that used to live here

7.5The draw, and two pity systems chasing different things

Count-proportional, without replacement

Draws are count-proportional over the PackConfig snap pool: weight = copies × chapterMult. Rarity is therefore a property of the pool and drifts as the pool depletes; the pool is rebuilt only on album advance. The old per-pack rarity probability grid was deleted because it multiplied the pool counts — rarity was applied twice. Pack tier now differs only by Cards/Open and the pity table.

Rarity pity — indexed by consecutive misses, not by card slot

Target selection is the highest rarity that still has copies when PityForceHighestRarity is TRUE. That doubles as the empty-tier fallback: Gold ships at Qty 0, so a 6-star pack's pity resolves to 5-star rather than chasing an undrawable card. When the flag is FALSE the target is any rarity above the pool's most-stocked one — a softer "better than what this pack usually gives".

The second, independent mechanism is the dry streak, and it chases a new card rather than a rare one: after 3 consecutive packs with zero new cards, the last card of the next pack is forced to be an unowned type. Reset on any new card and on album advance.

Chests read the CHEST PURCHASING panel — a minimum star balance plus a linear urgency ramp from the start day to an end-of-season buy probability — instead of the hardcoded "greedy sweep at 85% of the season" they used to. Missing parameters degrade to "never buy" rather than silently reverting to the old behaviour. Each successful roll buys the most expensive affordable chest, opens its reward pack, and rolls again.

Standing flag — the pity config semantics were never documented

The sheet's PACK PITY CONFIG block never said what its numbers meant. The first reading was wrong in a way that quietly changed every rarity number in the model. This is the project's canonical example of why undocumented config semantics are a blocking question, not a flagged assumption.

Sheet contract. Part D · D28, D34, D37, D40

Tower of Fortune — the first source that spends

Mighty Doors is the first source in the model that spends a resource, the first whose payout is gated on a decision rather than on reach, and the first where the player's wallet feeds back into their income. None of that fits measured × R × D × T, and there is no measured anchor to fit it to — the event has never run.

8.1What the event is, and why it needed a state machine

bottom-up · E[banked per run] × runs ⚙ ToF sheet (was MD) 📊 data_econ hc_balance percentiles resource 20: ToF_Ticket

The player spends one ticket to start a run. A run is a ladder of 60 stages; at each stage four closed doors are shown and the player picks one. Most doors hold a reward; one holds a Pig. Picking a reward door banks it into a temporary pot and advances one stage. Picking the Pig interrupts the run and puts the whole pot at risk.

Two decisions sit inside the expectation, and the model had never had one before

Every other simulated source pays on reach — a monotone function of effort or luck. Here the payout depends on when the player cashes out and whether they pay to continue. Both are choices, both are unobserved, and the second means the player's HC balance feeds back into their HC income. Both enter as explicit, named, editable inputs on the sheet rather than being buried in a formula.

8.2Pricing one run — a forward walk over (stage, continues, top-ups)

the model
SIMULATED[res] = E[banked reward per run][res] × runs over the window

  state P[k][t] = probability of being about to attempt the current stage,
                  having bought k continues and used t top-ups
  walk stages 1..cashOut; at each, resolve deaths in an inner loop over k
  bank = the WHOLE ladder up to cashOut, paid only if the run banked

Walking stage by stage keeps the state to a (kMax+1) × (topMax+1) grid. The ladder length is the continue cap — a rung with no price cannot be sold — and Max Continues per Run can lower it. The reward is banked all-or-nothing: bank[res] += stage.reward × P(reward | survived) × pBank summed over every stage up to the cash-out point.

Averaging over wallets, not just over stages

The whole walk is repeated at each of the four hc_balance percentiles from data_econ and averaged — the same way collections average a milestone ladder over the progress percentiles. p50 alone would erase the tail that actually reaches the deep rungs. A Coin Balance override on the sheet replaces all four for one segment, which is how the MAX ceiling row gets a wallet no real player has.

8.3The continue decision — willingness times affordability

Continue Take-Up on the sheet is the segment's baseline willingness after meeting a Pig. Willingness alone would let a 0-9 player buy the 1,890-coin rung as readily as the 50-coin one, so it is gated by what is actually in the wallet:

pc(k) = ContinuePseg × A( balancek ÷ costk+1 )

A(r) = 0                       when r < 1 — a HARD floor: you cannot buy what you cannot afford
       = (r − 1) ÷ (r − 1 + h)  otherwise; h = TOF_AFFORD_H = 1
Payers get exactly one top-up — and without it the model said the wrong thing

Measured payer balances are lower than non-payer balances in every segment — they spend what they buy: 100+ PAYER p50 = 74 against NONPAYER 107. Read literally, the model therefore said payers continue less. So once per run, a payer who cannot afford the next continue buys coins and takes it anyway at full willingness (TOF_PAYER_TOPUPS = 1, user decision). That is the third state dimension the walk carries. A gate holds it in place: nonpayer spend 0.00 against payer 49.33 on a fixture where one rung costs 50.

8.4The ticket budget — runs are earned, not configured

Tickets are earned, with no storage cap (deck p9: daily login, event rewards, shop offers). So the number of runs is not a config number — it is whatever the rest of the calendar pays out. ToF_Ticket is resource 20 and is priced by the same bottom-up lane the envelopes use, because it has the same measured anchor of zero.

10The windowed view — a slice, not a second engine

ECOGAINS_SIM_7_DAY / ECOGAINS_DIFF_7_DAY take the same arguments and spill the same grid as the full-window pair, restricted to WIN7_FIRST_DAY..WIN7_LAST_DAY — currently days 6–13, which is 8 days (the _7_DAY naming is the user's; the constants are the truth).

It is not a copy of the engine. A copy was requested, but every .gs in an Apps Script project shares one global namespace — a second RESOURCES, Context, timedCore_ or onOpen would silently override the engine's by load order. That is the failure mode that produced both the "all events zero" mystery and the vanished menu. The file declares seven new prefixed names and calls the engine for everything else.

method — sum the daily allocation, do not re-simulate
SIM_7 [cat][res] = Σd = FIRST..LAST  dailySeries_(cat, seg, payer, isNew = true )[d][res]
DIFF_7[cat][res] = SIM_7 − Σsame d  dailySeries_(cat, seg, payer, isNew = false)[d][res]

Edge behaviour follows the placement family, which is the point of reusing §9 rather than inventing a windowing rule: a leaderboard instance straddling the edge counts in full if it ends inside, and not at all if it ends outside; a collection contributes only the accrual share landing inside; envelopes follow their source's placement.

The invariant that keeps it honest

Set the constants to 1 and 33 and these functions reproduce ECOGAINS_SIM / ECOGAINS_DIFF bit for bit — ~5e-12 across every segment × payer × category × resource. That single check makes it structurally impossible for the derived view to drift from its parent, and it keeps working when either side changes.

11Display and recalculation plumbing

Google only re-runs a custom function when its ARGUMENTS change. SpreadsheetApp reads inside the function are invisible to the dependency graph, so config edits do not trigger a recalc by themselves. Every ECOGAINS_* formula therefore carries a trailing sim_refresh!$A$1 nonce argument.

How gates rot — three failure modes, all hit in this project

  1. Asserting ABSENCE. "SP_v2 absent → falls back to base" and "RM_1st/RM_2nd absent → falls back to RM" were true when written and became false the moment the workbook shipped those sheets. A gate that asserts something does not exist is guaranteed to rot. Assert the BEHAVIOUR, and exercise the fallback by creating the condition: snapshot the sheet, delete it, assert, restore.
  2. Sampling a point that goes inert. The SPT tier gates ran on 40-99, whose token total exceeds the ladder on both sides — so "tier drops" could never pass again, no matter how correct the engine was.
  3. Freezing a config value into an assertion. "Flash Race pays Coins 50" broke when the Race sheet was regenerated from live server configs. It now re-derives the expectation from the ladder and compares.

Rule of thumb: an assertion should be recomputed from the same inputs the engine reads, never copied out of one workbook export. Five more gates froze a past config in D24b — a pity gate naming the tier that forces highest rarity (the ladder shifted when the 6th pack tier was retired), a gate asserting no pack ladder had been authored yet, and a single-seed rarity check that was a coin flip dressed as an assertion. The fix is always to assert the RULE with a mutation fixture, never to weaken the assertion.

15The Sim per Segment rollup

A grouped rollup of the window totals: per resource × segment × payer, the gains collapsed into four source groups (PAID / ADS / CORE / META), plus a per-earner NET view answering "if player spend behaviour does not change, what happens to the net position of this currency?" Menu-run, not a custom function, because it writes both values and formulas.

cur_net  = gain_pe − spend_pe
new_net  = gain_pe + (M − G) − spend_pe      the engine movement ADDED on; spend UNCHANGED
net_diff = new_net − cur_net = M − G

G = the CURRENT gains total · M = the SIMULATED gains total, both per earner
Why additive and not gain_pe × (M/G)

The engine's G covers only the modelled categories, while data_econ's gain covers the whole faucet — workbook (9) measured gain_pe ≈ 1.8 × G for HC and Slingshot. The ratio form silently extrapolated the redesign onto faucets the engine does not model and overstated the movement by that same 1.8×. Additive moves exactly what the engine actually simulates and carries everything else. Worked: gains 700, spend 600, G = 250, M = 235 → cur_net +100, new_net +85, net_diff −15 — exactly the engine's movement. The ratio form would have said +58, a −42 swing, treating 450 HC of unmodelled gains as if the redesign had nerfed them too.
